LENS: engineering
VERDICT: MERGEABLE AFTER FIXES — the core mechanisms hold under probes and mutations, but the masking hides parallel tool outputs the model has never seen, and one bash-written entry line (or a NUL in a query) breaks search_memory, both with small local fixes.

WHAT THE IMPLEMENTATION GETS RIGHT
- Anthropic marks are repeat-gated and live only on copies. Marking the caller's block in place (mutation `mut_mark`) fails 12 of 14 tests, including `NoMutationTests::test_the_callers_messages_are_never_marked_and_marks_never_pile_up`. Each adapter belongs to one agent (`_runner_cache`, `agents/base.py:1672`), so one agent's digests never evict another's.
- The quantized trim does what D-5 promised. In a 600-iteration simulation through the real masking and trim middlewares (3 seeds), the first kept message moved on 13/281, 10/254, and 11/283 calls once trimming began. With main's exact-cap trim on the same views it moved on 265/281, 228/254, and 275/283. `_greedy_keep` is main's algorithm unchanged.
- Recall copies text from disk, and its bookkeeping refusal holds against Windows path aliases. `SUPERSEDED.JSONL`, `superseded.jsonl.`, `superseded.jsonl `, `superseded.jsonl::$DATA`, `entries.jsonl::$DATA`, and `./superseded.jsonl` all resolve to the real name and are refused. `superseded.jsonl:$DATA` and an 8.3 alias pass the check but read nothing ("File does not exist.").
- The bash head+tail keeps memory bounded (H+T bytes plus a count). The omitted count is held in a one-item list, so it survives `wait_for` cancellation. The timeout test with more than the cap is not skipped on Windows and passes.

FINDINGS

R-E1 [Blocker] [failure modes] vidbyte/middleware/compaction/windows.py:143-161 (wired at agents/infinite/agent.py:91, launch.py:298, recall.py:174) — Masking hides outputs of the newest parallel batch before the model has read them, and a re-issued batch is masked again
  Evidence: `compact` counts each scoped tool's results newest-first, one message at a time, and does not know which results the model has already answered. In `probe_mask_batch.py`, the newest turn is 5 parallel `read_lines` results, in both Anthropic and OpenAI shape. 2 of the 5 are masked on the very call that should show them. Re-issuing the same 5 calls in order masks 2 of the new batch again. In `probe_mask_rounds.py`, a model that re-calls only what it finds masked needs 2 model calls to see a batch of 4 or 6, and 4 calls to see a batch of 10 (7 → 4 → 1 → 0). Every masking test (test_infinite_memory_economy.py:138-254, test_compaction_windows.py) makes one call per turn.
  Failure: The user's premise is that the agent "no longer needs" what gets pruned (request.md:19). Here the generators, verifiers, and retriever are told "call it again" about output they never saw. Each extra round re-sends the full prefix. That is a cost increase in the PR whose goal is cost, and the retriever has only 8 iterations to spend. A model that re-issues the whole batch loops until `max_iterations`, the loop class request.md:58 and :121 forbid for dedup.
  Smallest fix: When a `tools` scope is set, never compact a tool_result that comes after the last assistant message, which is the batch awaiting the model's next turn. Those results still count toward `keep_recent`, so on the next call the older ones are masked as before. I checked this fix as a scratch plugin (`mut_mask_batch.py`). All 60 tests in test_compaction_windows.py, test_infinite_memory_economy.py, and test_context_compaction_middleware.py pass, and both probes then show 0 masked and 0 extra rounds. Add a test: a newest turn of 5 parallel `read_lines` keeps all 5 whole, and the next turn masks only the oldest 2.
  Spec IDs: INV-2.3 (implemented literally; the spec does not cover parallel batches), AC-2.1, NG-5, EC-2.2, request.md:19, :58, :121

R-E2 [Blocker] [error handling] vidbyte/tools/builtins/code_search/search_memory.py:121-122 with vidbyte/lib/util/fulltext.py:58-72 (and search_memory.py:74) — One entry line holding a lone-surrogate escape fails every later search, and a NUL in a query raises an FTS5 syntax error
  Evidence: In `probe_queries.py`, an `entries.jsonl` line with `"text": "zeta bad \ud800 here"` (valid JSON) makes `search_memory("zeta")` raise `UnicodeEncodeError`, on the first call and again on the second. `workspace.entries((1,))` still reads the same file. `_entry_rows` catches only shape errors (137-151). The encode error is raised later, by `executemany` inside `replace`, after `_delete` has already committed the removal of that source's old rows in a separate transaction. `fingerprint` stays stale, so every later call retries and fails. `execute` catches only `ConfigurationError` (80-85). The queries `"zeta\x00"` and `"zeta \x00x"` raise `sqlite3.OperationalError: unterminated string`. The workspace itself refuses lone surrogates when it writes (workspace.py:276-280, `@intent unwritable-entries-are-refused-first`). So this line can only come from bash or a developer, which is exactly the case INV-8.8 exists for.
  Failure: Every `search_memory` call, and every recall pre-search, fails for the rest of the workspace object's life. The runtime wraps each failure as "Tool execution failed: 'utf-8' codec can't encode…". INV-8.2 ("No query text can raise an FTS5 syntax error") and INV-8.8 ("never fails a search") are both violated as written.
  Smallest fix: In `_entry_rows`, call `label.encode("utf-8")` and `text.encode("utf-8")` inside the existing `try`; `UnicodeEncodeError` is a `ValueError`, so the bad line is skipped. In `execute`, treat `"\x00"` as whitespace before splitting the query. In `replace`, run the delete and the insert in one `with connection:` transaction, so a failed insert keeps the old rows. Add two tests next to `test_a_malformed_entry_line_is_left_out_and_never_fails_a_search` and `test_fts5_syntax_in_a_query_is_searched_as_text_and_never_raises`.
  Spec IDs: INV-8.2, INV-8.8, EC-8.1, T-1, FR-8.1

R-E3 [Major] [data and scale] vidbyte/tools/builtins/code_search/search_memory.py:104-127 (via code_search/base.py:62, :93, :115) — A search on an already-built index still walks, re-resolves, and reads every workspace file while holding the shared lock, about 10× over NFR-8.1 at the caps

  Failure: NFR-8.1 (under 50 ms warm) is missed by about 10×. INV-8.9 holds the lock across the refresh, so a 20-pair batch's searches queue behind each other, and the last waits about 10 s.   Smallest fix: In `_lookup` alone, list files with rglob + `should_ignore`, and derive each source from `path.relative_to(root_dir)` instead of resolving twice. Stat first, and run the text sniff (`open().read(2048)`) only for files whose fingerprint changed. Pass `retain` a set. Keep the lock across the index mutation and the search. Add a coarse benchmark for NFR-8.1; the test plan (line 111) leaves it untested.
  Spec IDs: NFR-8.1, INV-8.9, D-11, EC-8.4
