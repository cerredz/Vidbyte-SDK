LENS: engineering
VERDICT: NEEDS REWORK — on Windows, a model-supplied prompt, model id or rule passes through the `grok.cmd` shim into cmd.exe and runs as a shell command (T-2), and three failure paths break INV-14, INV-10 and NFR-2 in ways a scratch run reproduces.

WHAT THE IMPLEMENTATION GETS RIGHT (max 4 bullets)
- Every peer goes through one bounded close path. `NativePeer` builds `McpStdioTransport` with `exit_grace_seconds=G`, `shutdown_timeout=K` and `stop_process_tree=True` (vidbyte/harnesses/native/hostkit/peers.py:52-55). On POSIX, `ProcessStopper.stop_tree` runs the group stop even after the leader has exited, and every wait after a kill is bounded.
- Secrets stay out of argv. The opencode password is fresh per host and travels only in the child's environment (opencode/server.py:32, 63). Every opencode path segment is quoted whole with `quote(segment, safe="")` (opencode/client.py:106). The Muse reap mark is checked against `MUSE_PEER_MARK_PATTERN` before `wsl.exe` runs (muse/launcher.py:173), and `MUSE_REAP_SCRIPT` has LF line endings only.
- The tool boundary holds INV-7. `NativeHostTool.execute` has one try that maps NativeHostError, then ConfigurationError, then `Exception` (native_host_tool.py:173), so only `CancelledError` propagates.
- The Grok exit path is bounded as the spec says. It interrupts, then waits `asyncio.wait(tasks, timeout=G)`, then closes every peer concurrently (grok/host.py:122-130). The turn table caps finished turns FIFO at `NATIVE_FINISHED_TURN_LIMIT` (hostkit/turns.py:101-102).

FINDINGS (ranked, max 15)

R-E1 [Blocker] [security] vidbyte/harnesses/native/grok/cli.py:74 — On Windows, a caller-supplied prompt, model id or allow/deny rule reaches cmd.exe through the `grok.cmd` shim and runs as a shell command
  Evidence: Grok puts caller values into argv as single `--name=value` elements: `"--single=" + one_shot.prompt` at cli.py:74 and :80, `"--model=" + ...` at cli.py:105 and :112, and `"--allow=" / "--deny=" + rule` in `_run_flags`. The module itself states "On Windows shutil.which returns the grok.cmd shim, which CliRunner and the peer transport start like any program" (cli.py:9). `CliRunner._start` resolves the program with `shutil.which` and passes it to `create_subprocess_exec` (lib/process/runner.py:154-157). For a batch file, that runs `cmd.exe /c`, and cmd.exe re-parses `list2cmdline` quoting (the BatBadBut class of bug). Scratch `cmd_injection.py` built the argv the same way and ran it through `CliRunner` with a `.cmd` launcher. With the prompt `hi" & echo pwned> PROMPT_INJECTED.txt & rem "`, which `GrokOneShotRequest` accepts, it printed `prompt via --single= | exit 0 | marker created: True`. With the model `x&echo>MODEL_INJECTED.txt`, which the record accepts because it has no whitespace and no leading `-`, it printed `model via --model= | exit 0 | marker created: True`. The PR's own Grok acceptance tests run through a `.cmd` shim on Windows (tests/features/grok_host/test_grok_host_acceptance.py:9), but only with benign values.
  Failure: A hostile or confused model calling `run_grok_once`, `fork_grok_session` or spawn/continue (where the peer argv carries `--model=`) runs arbitrary commands as the user. This bypasses `permission_mode`, the deny rules and the default `PermissionPolicy`. It is exactly the "argv injection (`model` …)" that T-2 must prevent. The mitigation "values go into argv only in `--name=value` form" holds for execve, but not for a batch launcher. D-19 already rejects the `.cmd` shim for `wsl.exe` because "its cmd.exe layer breaks argument passing".
  Smallest fix: On win32, have `GrokCli.resolve_launcher` refuse a resolved launcher ending in `.cmd` or `.bat`. It should prefer the installer's `~/.grok/bin/grok.exe` fallback, and otherwise raise `grok.not_installed` or `configuration.invalid_argument` naming `grok_command`. Add a Windows test that sends a prompt and a model containing `"&%^` through a `.cmd` launcher and asserts that no side effect occurs.
  Spec IDs: T-2, D-19, INV-9, request.md §D

R-E2 [Major] [failure modes] vidbyte/harnesses/native/hostkit/turns.py:46 — The session-busy check compares ids case-sensitively, so an upper-cased UUID starts a second live turn on a busy Grok or Muse session
  Evidence: `RecordFieldValidator.require_uuid` accepts both cases and does not normalize them (lib/dataclasses/validation.py:31). `continue_grok_session` validates the id and then reserves the raw string (grok/host.py:262-264), and Muse does the same (muse/host.py:255). The table tests `session_id in self._busy_sessions` exactly (turns.py:46). The PR already treats these ids as case-insensitive elsewhere: `new_session_id ... .lower() == session_id.lower()` (grok/host.py:302). Scratch `uuid_case.py` ran against the fake Grok peer. A same-case continue gave `grok.session_busy`. An upper-case continue printed `ACCEPTED -> second live turn on 62B9EC90-B97E-422B-BDAC-1D3E3C494AF0 while 62b9ec90-b97e-422b-bdac-1d3e3c494af0 is live`.
  Failure: A vendor that parses the id as a UUID would receive two concurrent prompts on one session. RFC 9562 reads UUID hex case-insensitively. The result is interleaved history, a double spend, and two drivers answering the same session's approvals. A model can trigger this just by changing the case of an id. How the real vendors handle case was not verified, because no real `grok` or `muse` was launched.
  Smallest fix: Lower-case the id right after `require_uuid` in the Grok and Muse continue, fork, read and usage paths, so the busy key and the wire value are canonical. Add a test that continues on the upper-cased id of a live session and expects `session_busy`.
  Spec IDs: INV-14, EC-9, T-2

R-E3 [Major] [failure modes] vidbyte/harnesses/native/opencode/turn.py:259 — One transient HTTP 500 on any watcher poll fails the turn locally without sending an abort, leaving a server turn that nobody watches and that the SDK cannot stop
  Evidence: `_count_failure` re-raises every error outside `_COUNTED_FAILURES` (`OPENCODE_SERVER_UNREACHABLE`, `OPENCODE_PROCESS_EXITED`; turn.py:55, 259-260). The `raise` path in `run` (turn.py:105-107, 138) sends no `POST …/abort`. Only the EC-155 retry path aborts (turn.py:275). Scratch `opencode_poll_500.py` used the fake server with a single 500 on `GET /permission` and printed `wait raised: opencode.api_error`, `server still busy: {'type': 'busy'}`, `aborts sent so far: 0`, `interrupt_opencode_turn was_running: False | aborts sent: 0` and `continue raised: opencode.session_busy`.
  Failure: The server-side turn keeps running and spending, and nobody answers its permission or question requests (INV-10). `interrupt_opencode_turn` reports `was_running=False`, and every `continue_opencode_session` on that session is refused as busy until opencode ends the turn by itself. That may be never if the turn is parked on an approval. The same leak follows the EC-58 `protocol_mismatch` and EC-86 paths, and EC-87's give-up.
  Smallest fix: In `OpencodeTurnWatcher.run`, before raising a turn failure, send one best-effort `POST …/abort` bounded by `request_timeout_seconds` with `NativeHostError` suppressed, as the EC-155 path already does. Add a test with a single 500 poll that asserts the abort was sent.
  Spec IDs: INV-10, INV-13, EC-59, EC-87, D-9, G-3

R-E4 [Major] [failure modes] vidbyte/harnesses/native/muse/host.py:148 — `MuseHost.__aexit__` waits for its drivers with no bound, so a Muse that goes silent during an approval holds exit for `control_timeout_seconds` (30 s by default, up to 600 s) instead of the NFR-2 14 s
  Evidence: `await asyncio.wait(tasks)` has no timeout (host.py:148). Unlike Grok (grok/host.py:126), it never closes the peers itself after G. The grace deadline set by `close_after_grace` (muse/turn.py:154-158) is checked only between frames (turn.py:116). The in-turn peer calls carry no `timeout_seconds`, so each waits up to `control_timeout_seconds`: `approval/decide` at turn.py:212, `userInput/cancel` at turn.py:233, and the in-loop `turn/interrupt` at turn.py:130. Scratch `muse_aexit_bound.py` used G=0.3, K=0.5, `control_timeout_seconds=10`, and a fake peer that is silent on `approval/decide` and `turn/interrupt`. It printed `silent_decide=False: __aexit__ took 0.08s` and `silent_decide=True: __aexit__ took 9.06s (NFR-2 bound ... = 3.60s)`.
  Failure: With the defaults, `__aexit__` blocks for about 30 s, and so does cancellation of the enclosing task, since `__aexit__` runs on that path too. That breaks NFR-2 (P0) and the EC-8 "within the NFR-2 bound". Past the turn ceiling, the DEADLINE interrupt at turn.py:130 has the same stall of up to 30 s before the grace even starts. The existing exit tests (test_muse_host_process_bounds.py:170) use a peer that ignores interrupts, but never one blocked in a handler.
  Smallest fix: Do what Grok does. Use `await asyncio.wait(tasks, timeout=NATIVE_STOP_GRACE_SECONDS)`, then close the remaining drivers' peers concurrently, which fails the pending call, then wait for the tasks. Add the silent-`approval/decide` exit test.
  Spec IDs: NFR-2, EC-8, INV-4, D-23, request.md §D ("reaped on every exit path, including cancellation")

R-E5 [Major] [failure modes] vidbyte/harnesses/native/muse/launcher.py:128 — In WSL mode, short-lived Muse peers never forward `META_API_KEY` into the distro, while turn peers do
  Evidence: `peer_environment(None)` returns `NativeChildEnvironment.build({})` with no `WSLENV` change (launcher.py:128-129). `check_muse_ready` (muse/host.py:159) and every `_new_peer(None)` read peer use it, including `list_muse_models` (host.py:190), session list, read and page, fork, and usage. Scratch `muse_wslenv.py` used a placeholder key and printed `turn peer WSLENV: WT_SESSION:META_API_KEY/u:VIDBYTE_PEER_MARK/u` and `read peer WSLENV: WT_SESSION`. D-18 lists "`WSLENV` extended with `META_API_KEY/u` when that variable is set" as the vendor overlay. §9.3 (spec.md:1552) does the same for the Muse peer environment.
  Failure: A user whose key exists only in the Windows environment gets working turns, while `check_muse_ready` and `list_muse_models` run in the distro without the key. Readiness then cannot predict turn behavior, and any read that needs auth fails with a misleading code. Whether `model/list` needs the key was not verified, because no real muse was launched.
  Smallest fix: In `peer_environment`, add the `META_API_KEY/u` entry whenever `wsl_mode` is on, and add the mark entry and variable only when `mark` is not None. Add a test for the read-peer `WSLENV`.
  Spec IDs: D-18, T-8, FR-19

R-E6 [Minor] [data and scale] vidbyte/harnesses/native/muse/turn.py:71 — Muse keeps every approval and user-input decision in memory and applies the INV-16 cap only when it builds the result
  Evidence: `_decisions.append(...)` is unconditional (turn.py:209, 214, 217, 219, 231). The cap appears only at `decisions=tuple(self._decisions[:cap])` (turn.py:282-283). opencode caps on append (opencode/turn.py:254-258). `NativePeer.inbox` is an unbounded `asyncio.Queue()` (hostkit/peers.py:46) and keeps filling while a handler waits on a peer call (R-E4).
  Failure: A peer that floods unique approval ids grows `_decisions`, `_decided` and `_cancelled_inputs` for the whole turn, which can last up to `max_turn_seconds`. The result output is unchanged.
  Smallest fix: Cap `_decisions` on append and count the overflow, as opencode does.
  Spec IDs: INV-16, INV-10

R-E7 [Minor] [data and scale] [scope-adding] vidbyte/lib/http/transport.py:61 — Every opencode watcher request opens a fresh `httpx.AsyncClient` and connection, four times per second per live turn
  Evidence: `HttpTransport.request` wraps each call in `async with httpx.AsyncClient(...)` (transport.py:61). The watcher makes four calls per poll (opencode/turn.py:176, 184, 185, 191) every `OPENCODE_POLL_INTERVAL_SECONDS = 1.0`.
  Failure: With `max_live_turns` turns, that is 4×N new loopback connections per second. On Windows they pile up in TIME_WAIT. Behavior is unchanged at small N.
  Smallest fix: Let `HttpTransport` take a caller-owned client for its lifetime, held by `OpencodeClient` from `__aenter__` to `__aexit__`.
  Spec IDs: INV-16 (spirit), AGENTS.md principle 5 (HttpTransport as the canonical helper)
