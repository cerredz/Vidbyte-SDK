VERDICT: SOUND WITH FIXES — the architecture fits the repo and its pins, but content search misses the host's own threads, two goal paths dead-end, the side chat has three safety gaps, and one tool kills processes, so the spec needs changes before S2 writes tests.

WHAT THE SPEC GETS RIGHT
- The raw passthrough (`CodexJsonObjectResponse` + `parse` on the worker inside the call) matches how the SDK works. `CodexClient.request` requires a dict and then calls `response_model.model_validate`, so a passthrough model, with parsing inside `connection.call`, keeps one call record per request and the existing `PROTOCOL_MISMATCH` mapping.
- Mixins over `CodexHostCore` really do keep both surface pins: `vars(CodexHost)` does not see inherited methods, and the boundary pin uses `inspect.getmembers`, which does. The 25 `CodexHostOperation` members go after `FORGET_CODEX_TURNS` and before `LAUNCH_CODEX_SUBAGENTS`. That satisfies both order pins (`test_codex_host_helper_surface.py:244-250` pins the whole tail after `START_CODEX_REVIEW`; `test_codex_host_hardening_records.py:113-116`).
- The stable/experimental classification of every new method is correct against `methods.txt` and the two schemas, including the stable `origin`/`tokenBudget` on goal set/clear. Experimental fields are injected after validation and refused locally, as settled.
- `GitWorktrees.add` over `CliArgv`/`CliRunner` is the right canonical helper. It reuses the PATH-only program lookup, `launch_failure`, and process-tree stop on timeout or cancel. The `SEPARATE` style refuses option values that start with a dash, and `--` goes before the path.

FINDINGS

R-1 [Blocker] [L5] §6.1 INV-39 / §9.2 — `search_codex_thread_content` never finds the threads CodexHost creates, because it omits `sourceKinds`
  Evidence: INV-39 says "It sends one `thread/search {searchTerm, archived?, cursor?, limit?}`", with no `sourceKinds`. INV-40 and D-24 add them for `thread/list`, because "Omitted `sourceKinds` means 'interactive sources only'". The schema says the same for search: `schema-exp/v2/ThreadSearchParams.json:85-86` reads "When omitted or empty, defaults to interactive sources." Interactive means `[Cli, VsCode]` (`tui/src/lib.rs:779-784`: "`thread/list` treats omitted and empty `sourceKinds` as interactive-only…"). The repo assumes host threads are app-server sourced: the fake's default `FakeThread.source` is `"appServer"` (`tests/features/codex_host/codex_host_fakes.py:161`), and every existing helper listing sends `CODEX_HOST_HELPER_SOURCE_KINDS` ("every top-level source", `vidbyte/lib/constants/codex.py:402-403`; `thread_helpers.py:266`).
  Failure: A developer spawns threads through CodexHost, then calls `search_codex_thread_content("login")`. Codex filters to cli/vscode sessions, so the search returns none of the host's own threads, and no exec or sub-agent threads either. AC-33 asserts `sourceKinds` only for the listing, and the fake's new `thread/search` handler will not filter by source, so every test passes while the live feature is broken.
  Smallest fix: INV-39 sends `sourceKinds` = every `CodexThreadSourceKind` value, as D-24 does (or `CODEX_HOST_HELPER_SOURCE_KINDS` if sub-agent hits are unwanted, with that choice stated). Add the key to the §9.2 wire-params list and to AC-33's expected search params. Add an EC row: "a thread whose source is appServer is found".

R-2 [Major] [L9] §6 INV-12 (the load guard reused by INV-14, INV-35, INV-36, INV-37) — a paused goal on a thread that is not loaded blocks settings, memory mode, revert and inject forever, and the next step loops
  Evidence: INV-12 says "A stored goal whose status is not complete is refused with `CODEX_GOAL_UNFINISHED`". The guard reuses `CODEX_HOST_RESUMABLE_GOAL_STATUSES = frozenset({CodexGoalStatus.COMPLETE})` (`vidbyte/lib/constants/codex.py:427`), and its next step is "Pause the goal with pause_codex_goal or clear it with clear_codex_goal, or let it finish, then call again." Yet A-13, which `resume_codex_goal` already depends on, states that loading a thread whose goal is "`paused`, `blocked` or `usage_limited` does not restart it; only `active` does". A-13's "If wrong" clause even says the guard "would then refuse every status but complete", which implies it does not today. The spec contradicts itself.
  Failure: The thread is not loaded and its goal is `PAUSED`. `set_codex_thread_memory_mode(t, DISABLED)` raises `codex.goal_unfinished`, telling the caller to pause the goal. The developer pauses it (it already is paused) and calls again, and gets the same refusal. `BLOCKED`, `USAGE_LIMITED` and `BUDGET_LIMITED` goals behave the same way. The only exits are destroying the goal with `clear_codex_goal`, or spending through `resume_codex_goal` until it completes.
  Smallest fix: Give the slice-2 load guard its own constant, consistent with A-13: refuse only `ACTIVE` (and any status the enum does not know). Keep compact's `CODEX_HOST_RESUMABLE_GOAL_STATUSES` unchanged. If you keep complete-only instead, rewrite `CODEX_HOST_LOAD_GOAL_UNFINISHED_NEXT_STEP` so it never tells the caller to pause a paused goal, and change A-13's wording. Add an EC row for a paused goal on a thread that is not loaded.

R-3 [Major] [L1] §6 INV-31 / INV-32, §9.3 `CODEX_HOST_GOAL_RESUME_FROM_STATUSES` — a budget-limited goal can never be continued, so "goal control" is incomplete
  Evidence: The resume set is `{PAUSED, BLOCKED, USAGE_LIMITED}`, and INV-32 says edit "changes the objective and budget, never the status". Codex's TUI continues a budget-limited goal through edit: `edited_goal_status` maps `BudgetLimited | Complete => Active` (`tui/src/chatwidget/goal_menu.rs:133-143`). For `BudgetLimited` it offers "Commands: /goal edit, /goal clear" (`:113-115`). The spec's next step for a refused resume says "a complete goal is finished, so start a new one with run_codex_goal", and it says nothing about budget-limited (`CODEX_HOST_GOAL_NOT_RESUMABLE_MESSAGE` row).
  Failure: A goal stops with `BUDGET_LIMITED`. The developer raises the budget with `edit_codex_goal(t, token_budget=…)`; the status stays budget-limited. Then `resume_codex_goal(t)` is refused before anything is sent. The only path left is `run_codex_goal`, which clears the goal (`_start_goal_operation` clears first) and loses its accumulated usage and history. That is exactly what INV-31 exists to avoid.
  Smallest fix: Add `BUDGET_LIMITED` to `CODEX_HOST_GOAL_RESUME_FROM_STATUSES`. Document the order in the docstring, message and next step: "raise the budget with edit_codex_goal, then resume_codex_goal". Add an AC-26 case. Add an assumption beside A-1 that a status-only `active` set on a budget-limited goal whose budget was raised starts a turn. Edit stays status-free, which keeps every goal turn tracked.

R-4 [Major] [L7] §9.2 tool 41 / D-21 — `CleanCodexBackgroundTerminalsTool` lets a model kill background processes on any thread of the account
  Evidence: Row 41 is `clean_codex_background_terminals`, policy WRITE, with `thread_id`* and no ownership check. INV-38 only checks that the thread exists. Tool scope ownership exists only for turn handles (`vidbyte/tools/builtins/codex/_base.py:105` `require_owned(handle, …)`), so a thread id is never checked against the host. D-21 lists "terminals clean as developer-only" as the runner-up. The settled rule says destructive functions are never tools; it lists process spawning and deletion, and killing processes is as irreversible.
  Failure: A developer allows WRITE tools so that a model can spawn and continue threads. The model, confused or prompt-injected, calls `clean_codex_background_terminals` on a `thread_id` it found with `list_codex_threads`. That can be a user's own CLI session running a dev server or a long build, and its processes are terminated with no undo. Read-only tools cannot do this, but the WRITE policy is all-or-nothing.
  Smallest fix: Take D-21's runner-up. Make `clean_codex_background_terminals` developer-only: no tool, toolset 42, 16 new tools, and update every count in §8.3, §12.3 and §13 (that makes 9 no-tool operations in the `EXPECTED_ENUMS` row). Optional [scope-adding] Q-10: a tool restricted to threads this toolset's scope started (default not built).

R-5 [Major] [L7] §6 INV-27 step 4 / D-22 / T-2 — the read-only side chat can still write through the parent's Vidbyte tools, so T-2 overstates its control
  Evidence: INV-27 step 4: "The fork shares the parent's tool handler (hardening INV-28 step 7)". In `thread_helpers.py:229-231`, `handler = connection.router.handler_for(thread_id); if handler is not None: connection.router.register(fork_id, handler)`. T-2 counts "write files from a side chat" as handled because "The side-chat tool forces `READ_ONLY` (D-22)". D-22 says the tool "must never let a model add a second writer".
  Failure: The parent was spawned with Vidbyte dynamic tools, for example a file writer or bash. `READ_ONLY` constrains only Codex's own sandboxed commands. Dynamic tools run in-process in Vidbyte, outside Codex's sandbox. A model's side chat can therefore call the parent's write tool beside the parent's running turn, which is exactly the second writer D-22 forbids.
  Smallest fix: Narrow T-2 and D-22 to "Codex's own commands and patches are read-only; the parent's Vidbyte tools stay callable", and say so in the tool description and the method docstring. Optional [scope-adding] Q-11 (default not built): `StartCodexSideChatTool` refuses a parent that has a registered tool handler, or the side chat does not share the handler.

R-6 [Major] [L5] §6 INV-27 — the side chat starts a turn without the user-reviewer check that spawn, continue and resume run after the thread opens
  Evidence: In `host.py:786` (`_open_thread`) and `host.py:366` (continue), `if self._approval_handler is None and self._responses.routes_to_user(started|resumed)` refuses before any turn (hardening D-32). `CodexThreadHelpers.fork` returns `CodexThreadInfo`, not the fork response, so INV-27 steps 4-6 cannot run `routes_to_user`. `ThreadForkResponse` carries `approval_policy` and `approvals_reviewer` (checked with `V -I`: the same fields as `ThreadStartResponse`). Preflight's `reject_user_reviewer` sees only the request's own field, not a reviewer that comes from `config.toml` or the parent.
  Failure: On a host with no `approval_handler`, the parent's resolved reviewer is `user` (from `config.toml`). `start_codex_side_chat` forks, injects and starts a turn. The first approval request goes to a person nothing answers, and the turn stalls until its timeout, spending meanwhile. A spawned thread with the same configuration is refused before `turn/start`.
  Smallest fix: Add a step to INV-27 between 4 and 5. Apply `routes_to_user` to the `ThreadForkResponse` (widen its annotation, or have `fork` surface the flag). When it routes to a user, release the fork's handler and raise the existing reviewer refusal, naming the fork, before `thread/inject_items`. Add an EC row and an AC case.

R-7 [Major] [L6] §6 INV-20 / INV-21 / INV-22, NFR-3 — the stream window's lifetime is undefined: an abandoned subscription can pin it, and no host-wide bound is stated
  Evidence: INV-18: every live turn "owns one `CodexTurnEventLog` from the moment it is tracked", whether or not anyone streams. INV-21: "Once the turn has ended and no subscription is still reading, the kept events are released". INV-22: `stream_codex_turn` is a plain `def` that returns the iterator at once. Row 18: the log keeps "the subscriber cursors". NFR-3 bounds memory only "Per live turn" (4,096 events and 2,000,000 characters, plus Python object overhead the character count leaves out).
  Failure: A caller writes `s = host.stream_codex_turn(h)` and never iterates `s`, or breaks out of `async for` without `aclose()`. If the cursor is registered when the subscription is created, "still reading" never becomes false, and the full window stays alive while the turn stays tracked, until `forget_codex_turns`. A long-lived host running many streamed turns grows without bound. Even without leaks, N concurrent turns hold N × 2M characters with nothing that caps it at host level. Separately, INV-18 recomputes `turn.usage_delta()` (three `model_dump`s) per notification, on top of the `over_cap` call that already does so.
  Smallest fix: Define "still reading": a cursor is registered at the first `__anext__` and removed in a `finally`, on `aclose`, or on garbage collection (held weakly). Add an AC for a subscription created but never iterated: after the turn ends, the log holds only `ENDED`. State the host-wide worst case in NFR-3 (tracked live turns × the two limits). Have `on_event` compute the usage delta once and pass it to both consumers.
