**Hypotheses and attempts.**
- R-11: `Process.wait()` cannot mark the end of a run, because on Python 3.12+ it resolves only after every pipe has closed, which a grandchild holding the pipes can delay for good. Verified on Python 3.11 and in a scratch Python 3.13 venv; there is no local 3.12, so the remote Source / Python 3.12 job is the check for it.
- R-4: `shutil.which` on win32 always puts the current folder first, even with `path=`, so it cannot be kept. Adding `PATH`/`PATHEXT` members to `NativeEnvironmentVariable` was dropped because the surface test pins its members; they became constants. The bare-name lookup was lifted into `CliRunner.run` so `run → launch → find_program` stays one level deep.
- R-5: a raising helper inside `NativeErrorFactory` was rejected (it recreates the two-level chain R-3 removes), as were cross-harness imports, a new class, and an `is_thread_id` on the validator (more feature coupling in the canonical validator, R-22). The chosen helpers are static methods on existing classes, as pre-authorized.
- R-8: counting the quoted form needs `subprocess.list2cmdline` and UTF-16 units; the check runs only on win32 and only for the argv prompts (Grok, Muse). A WinError 206 that still happens maps to `OS_ERROR` (`launch_failed`) instead of `not_installed`.
- R-10: `asyncio.to_thread` cannot be cancelled, so the preparation runs as a shielded task and a cancel waits for it before removing what it made.

## Iteration 2 — 2026-10-15 15:20 — S5 repair agent (report `reports/S5-repair-2.md`)

**Defects in.** Re-review findings R-27 (Major), R-28 (Blocker), R-29 (Major) and R-30 (Minor, scheduled), each with S2 regression tests (`4b5eacad`). At `b3201a2c` the pack gave `12 failed, 424 passed, 2 skipped`: R-28 ×2 (launcher), R-27 ×1 (runner), R-29 ×8 (arguments), R-30 ×1 (process_bounds); all 12 reproduced here (`12 failed, 426 deselected` with `-k`). No gate was red at the start besides these tests. R-31 was already done by S2, and R-32 is a follow-up.

**Hypotheses and attempts.**
- R-28: start taskkill by an absolute path built from `SystemRoot` (`C:\Windows` when unset), read at call time. A root that is not absolute starts nothing, and the leader kill still runs. `CliRunner.find_program("taskkill")` was not tried, because the verifier had measured that it fails 9 tree-stop tests: the pack's sandbox `PATH` is one empty folder. Probe `rr2_stop_tree.py head realpath|sandboxpath` with `NoDefaultCurrentDirectoryInExePath` unset now gives `planted taskkill.exe started=0 … grandchild alive after stop=False` on 3.11 and 3.13 (before: `started=1`, alive). A scratch probe of the root branches gave `unset: taskkill started=True`, `relative: taskkill started=False`, `real: taskkill started=True`, with the leader stopped every time. `git grep` over the PR's `vidbyte/` files finds only two launches: the runner's `subprocess_exec`, which `find_program` feeds on win32, and this taskkill. No other bare program name is launched.
- R-27, first fix (as the review prescribed): move the post-exit `_finish_readers` and its conditional `stop_tree` inside the guarded `try`, and give the `TimeoutError` branch its own `_finish_readers`. It worked on win32: `rr1_cancel_window.py` gives `stop_tree calls=1; reader tasks pending=0` on 3.11 and 3.13, and the plain, held-pipe and timeout rows are unchanged. **It was not enough on POSIX.** GitHub CI on `4dc11f2c` (run 38783357799) failed the POSIX-only half of the test on 3.11 and 3.12: `AssertionError: INV-9 / R-27: the grandchild outlived the cancelled run`. The test's `alive` reads `/proc/<pid>/stat` and counts `Z` as dead, so the grandchild was still running. Root cause: once the leader is reaped, `stop_tree`'s only wait, `_bounded_wait` on the leader, returns at once, so the stop ended microseconds after `killpg(SIGKILL)`. The kernel had not yet run the grandchild's exit (`exit_mm` of a Python process comes before the zombie state). The scheduled win32 runs could never show this, because the test skips the grandchild check there. WSL1 (`MuseUbuntu1`, Python 3.12.3, standalone probe `s5-repair-2/r27_posix_probe.py`) does not reproduce it either: its kill completes the exit synchronously, so 20 of 20 rounds already showed `Z`. WSL2 cannot start on this machine, because virtualization is off.
- R-27, POSIX follow-up. Three approaches were weighed. (a) After the group KILL, poll `os.killpg(pid, 0)` until the group is empty, bounded by the grace. **Chosen**: it is portable POSIX, and a zombie that nobody reaps only holds the wait to its bound. (b) Wait for the readers' natural EOF before closing the pipes. Rejected: it covers only descendants that hold the pipes, and EOF (`exit_files`) comes before the zombie state (`exit_notify`), so a window stays. (c) Scan `/proc` for the group's members and wait until each is a zombie or gone. Rejected: Linux-only and O(processes). With (a), the WSL1 probe gives `states=['gone']; max propagate=0.011s`, and GitHub CI on `53d9f45a` is 4/4. The first version used a literal `os.killpg(pid, 0)` and lint A007 regressed (`256 finding(s), allowance 255`: "operational literal 0: operational context contains 'timeout'"). The fix is a named constant, not a baseline change.
- R-29: the new `NATIVE_WINDOWS_ARGV_PROMPT_MAX_UNITS = 30000` replaces the 24,000-character cap as the quoted-units ceiling, and the 24,000-character `require_text` cap is unchanged. The existing message (`… at most 30000 UTF-16 code units once quoted for the Windows command line; got 40000.`) already puts the ceiling before "command line", which is what the test's `find_in_order` needs, so the validator did not change. `rr3_cmdline.py`: prose of 24,000 and 23,999 characters (24,002 and 24,001 units) → accepted for Grok and Muse; 20,000 quotes or astral characters (40,000 units) → refused naming 30000.
- R-30: in `execute`'s `except CancelledError`, `await asyncio.shield(asyncio.ensure_future(MuseThreadRun._discard(preparing)))`. `rr4_double_cancel.py head` on 3.11 and 3.13: `cancels=2: … temp folders when CancelledError arrived=['tmp…']; 1.5s after the copy finished=[]` (before: the folder stayed for good); the single-cancel row is unchanged. The variant that loops until the cleanup is done was not built. It would hold INV-9's order for any number of cancels, but it swallows later cancels, so a skill copy that hangs could never be cancelled; the review leaves that choice to the owner.
- Heredoc trap: a Bash heredoc collapses `\\`, so a Python edit script turned `\taskkill` into a tab in spec deviation 23. That was fixed with the Edit tool, and the spec holds 0 tab characters.
