- **Repository Map (callout):** the Placement Rules are "binding for all new code, and the `AGENTS.md placement` workflow enforces it on every pull request by moving misplaced code to the location it names."
- **1. Keep Call Chains One Level Deep:** "a function may call another of its own functions, but that second function should not call a third." "Avoid defining functions inside other functions as well, unless an API requires a callback or a decorator."
- **2. Narrate Main Functions in Plain English:** "place short plain-English comments throughout the body, so that a reader can follow the whole feature by reading only the comments." "When you change the steps of a main function, update its comments in the same edit".
- **3. Build in Layers of Small, Single-Purpose Classes:** "`vidbyte/lib/` is the bottom layer, domain packages such as `agents/`, `tools/`, and `context/` build on it, and composition layers such as `pipelines/` and `paradigms/` build on those; nothing in `vidbyte/lib/` may import from a layer above it." "Keep files well below 1,000 lines". "If describing the job of a function or a class needs the word "and", it is probably two functions or two classes."
- **4. Use Validated Dataclasses:** core functions "take a dataclass as input and return a dataclass as output"; each "validates itself strictly when it is created, in `__post_init__`"; "Prefer `@dataclass(frozen=True, slots=True)`", "type any field whose value comes from a small, closed set as an enum".
- **5. Write Shared Logic Once, as a Canonical Helper in `lib/`:** "Before you write logic like this, look in `vidbyte/lib/` for a helper that already does it, and if one is close, add the option you need to it rather than copying it". "Logic that only one feature will ever need can stay with that feature".
- **Placement Rules / Dataclasses:** "**Every new dataclass is defined in `vidbyte/lib/dataclasses/<domain>.py`**" ... "Do not create `types.py`, `records.py`, `models.py`, or `schemas.py` modules next to the code that uses the dataclass." Exception 1: "A `*Settings` class that configures an agent lives in `vidbyte/agents/settings/`, or in the owning agent's own `settings.py` (for example `vidbyte/agents/jev/settings.py`)."
- **Placement Rules / Enums:** "**Every new enum ... is defined in `vidbyte/lib/enums/<domain>.py`**, and every public enum is added to the export list in `vidbyte/lib/enums/__init__.py`. There are no exceptions." "Any field, parameter, or registry key whose value comes from a small, closed set is typed with an enum from this folder, not a plain `str`."
- **Placement Rules / New JEV code** (precedent only, this is not JEV): "A new Jev-facing prompt is a new family under `vidbyte/prompts/prompts/`, with its key in `vidbyte/lib/enums/prompts.py`." Constants go in `vidbyte/lib/constants/<domain>.py`; "Never create a `types.py`, `enums.py`, or `constants.py`" inside the agent package.
- **Existing code:** modules that define dataclasses or enums elsewhere "predate these rules. Do not copy them as precedent."

## 4. Notes for the spec author

- Request assumes grep "with a scope (workspace/project/both)" (request.md:142); code shows `GrepTool` has one `root_dir` and a fixed spec name `"grep"` (code_search/grep.py:30), and `Tools.add` raises on a duplicate name (catalog.py:78-79), so two GrepTool instances cannot sit in one catalog.
- Request assumes bash is a preset tool on every agent (request.md:62,165); code shows `BashTool` is `ToolPermission.EXECUTE` and BaseAgent's default `PermissionPolicy()` allows only SAFE and READ (security.py:33-35); CodingAgent defaults to `PermissionPolicy.allow_all()` for this reason (coding.py).

The enum is string-selectable, so the runtime must refuse to build without its settings (runtime-boundaries.md; JEV precedent runtime.py:59-67).

A per-tool-call check (request C's bash-bypass scan "after every tool call") has no runtime hook; the per-call seam is middleware `after_tool_call` (context_compaction.py:63 is an example).
