# Spec: Let the SDK's gateway text modes (AUTO and VIDBYTE_MANAGED) use provider meta

> **TL;DR** — `ModelProvider.META` joins `VIDBYTE_MANAGED_TEXT_PROVIDERS`, the one set that decides which providers the SDK sends through the Vidbyte gateway. With that, a Muse call in the default `TextModelMode.AUTO` relays the developer's own Meta key in `X-Vidbyte-Provider-Key` (Meta bills them, Vidbyte bills its 2% fee), and a call without a Meta key, or in `VIDBYTE_MANAGED`, is Vidbyte-paid. No adapter, runner, or transport code changes. That was traced end to end and confirmed with an in-memory probe. *(r4)* The key matcher's Meta rule also changes: Meta documents its keys as `LLM_<numeric id>_<secret>` (https://dev.meta.ai/docs/authentication, read 2026-10-17), a shape the rule did not prove, so such a key in `api_keys` was refused or, beside a Kimi or DeepSeek model, sent to that vendor. The rule now proves both `LLM_` and the older `LLM|` form as `meta` and reserves both prefixes to it (D-8). The decision that matters most: keep `max_tokens` as Meta's cap field, because Meta documents it as an accepted alias that caps "reasoning tokens plus visible output tokens combined". The change also turns some Muse calls that fail today into billed calls: fallbacks, forks, and handoffs to Muse (EC-11), and compositions that tolerate a failed member or stage, for example the multi-provider grader when `META_API_KEY` is set (EC-16). There, a Muse member that was silently skipped now runs as an agent loop of one or more billed calls. The PR body discloses this. This PR merges only after cerredz/Vidbyte#710 is deployed, after ops has provisioned the backend's `META_API_KEY`, and after the pre-merge live check described in this PR has passed.

## Part A — Framing

## §1 Goal

Today the SDK refuses provider `meta` in both gateway modes. `TextModelConfig(provider="meta", model="muse-spark-1.1")` in the default `AUTO` mode raises at construction: "The Vidbyte gateway serves only: anthropic, deepseek, gemini, kimi, openai, xai. Use mode=TextModelMode.DIRECT to call meta with your own key." (observed at `base_commit`; the refusal is `_require_gateway_shape`, which reads `VIDBYTE_MANAGED_TEXT_PROVIDERS`). The only way to call Muse from the SDK is therefore `TextModelMode.DIRECT`, straight to `api.meta.ai` with no Vidbyte key, so Vidbyte earns nothing on Muse traffic ("the gateway refuses meta today, so Muse users skip Vidbyte's 2% fee entirely", §0). The backend half, cerredz/Vidbyte#710, adds `meta` to the gateway as a seventh provider. This PR is the SDK half: it lets the SDK send Muse calls there.

*(r4, S4 R-1)* A second defect sits in front of the same goal. Meta's authentication page documents keys as `LLM_<numeric id>_<secret>`: "API keys start with `LLM_`, followed by a numeric ID and the secret, separated by underscores" (https://dev.meta.ai/docs/authentication, read 2026-10-17). The matcher's Meta rule proves only `LLM|<id>|<secret>` (`KEY_FORMATS`, `provider_keys.py:53-55` at `base_commit`), and `LLM_` is not a reserved prefix. So a real Meta key in `api_keys` is refused at construction with M-6 when no configured provider takes a key that no prefix proves, as with the §4 snippet's `meta` and `anthropic`. That breaks the §4 path. When a Kimi, DeepSeek, Mistral, GLM, or MiniMax model is configured beside it, the key binds to that provider by elimination and is relayed to that vendor. The S4 verifier's probe shows both, byte for byte the same at `base_commit` and at the r3 head. Only the `META_API_KEY` path works today.

## §2 Objective

When this PR merges, `VIDBYTE_MANAGED_TEXT_PROVIDERS` in `vidbyte.lib.constants.jev` holds `ModelProvider.META` beside the six providers it holds today. Every existing gateway mechanism then applies to `meta` unchanged:
- construction-time shape checks;
- key matching and the relay header;
- the 32,768 output cap, sent as `max_tokens`;
- the 630 s timeout floor;
- same-key re-sends;
- status-only, credential-safe failure wording.

The README's managed-mode section names Meta among the served providers, in the output-cap guidance, and, by both key prefixes, in its Prefixes bullet. The comment above the set cites #710 as the source for `meta`. *(r4)* `ProviderKeyMatcher.KEY_FORMATS`' Meta row proves both Meta key shapes, `LLM_<numeric id>_<secret>` (the one Meta documents) and `LLM|<id>|<secret>` (kept, Q-7), and reserves both prefixes to `meta`. Its source comment and its row in the registries README's "Provider Key Format Sources" cite Meta's page. The two existing feature-test packs extend their per-provider tables to `meta`, and their two assertions that `meta` is refused change by design. *(r4)* They also gain a fake Meta key in the documented shape, and their one pin of the Meta prefixes changes by design. S2 owns that work (§13). The PR body states the merge prerequisites (§12.5): This PR merges only after cerredz/Vidbyte#710 is deployed, after ops has provisioned the backend's `META_API_KEY`, and after the pre-merge live check described in this PR has passed.

## §4 Developer usage

```python
import os

from vidbyte import Agent
from vidbyte.lib.config import TextModelConfig, TextModelMode
from vidbyte.lib.runners import TextModelRunner

# AUTO (the default): your Meta key sits in a mixed list, and the SDK
# matches it to meta by its prefix. Meta issues keys shaped
#   "LLM" + "_" + <numeric id> + "_" + <secret>
# and the older "LLM" + "|" + <app id> + "|" + <secret> form matches too.
muse = Agent(
    name="muse",
    system_prompt="Answer in one word.",
    provider="meta",
    model_name="muse-spark-1.1",
    vidbyte_api_key=os.environ["VIDBYTE_API_KEY"],
    api_keys=[os.environ["ANTHROPIC_API_KEY"], os.environ["META_API_KEY"]],
    fallback=["anthropic/claude-sonnet-5"],
)
print(muse.run("Say hi.").content)  # relays the Meta key; Meta bills you, Vidbyte bills its 2% fee

# VIDBYTE_MANAGED: Vidbyte's own Meta key; Vidbyte bills provider cost plus 2%.
paid = TextModelRunner(TextModelConfig(provider="meta", model="muse-spark-1.1", mode=TextModelMode.VIDBYTE_MANAGED))
print(paid.run("Say hi.").text)
```

Both calls reach Vidbyte's one gateway route instead of raising `UnsupportedProviderError`. The first carries the Meta key in `X-Vidbyte-Provider-Key` and never the Anthropic key. The second carries no provider key, although `META_API_KEY` is set. The developer no longer has to switch Muse to `TextModelMode.DIRECT`. *(r4)* The key can be in the shape Meta issues today (`LLM_`) or the older `LLM|` form. Either way it is matched to `meta` and to no other provider, so the developer does not have to move it out of `api_keys` into `META_API_KEY`.

Validation happens at construction. `_require_gateway_shape` admits `meta` only because the set now holds it, and it still refuses a custom endpoint. `ProviderKeyMatcher.match` proves a key of either Meta shape, `LLM_<numeric id>_<secret>` or `LLM|<id>|<secret>`, as `meta`. Both prefixes are reserved to `meta`, so a key that starts with either but does not fully match is refused with M-6 and never bound to another provider (r4, D-8). `credentials()` then checks that the key can be sent and is at most 512 characters. State is pinned once, in `TextModelRunner.__init__`: the keys, the 32,768 cap, and the 630 s floor. `MetaProvider` builds the same body it builds for `DIRECT`, and `VidbyteGatewayTransport` replaces the vendor URL and headers with the gateway's. Failures are caught in `_GatewayAnswer`: a 409, a 502, or an answer that is not JSON is re-sent with the same `Idempotency-Key`, and every failure is worded from its status alone.

## Part B — Behavior (this is the spec; everything else is framing)

## §6 Behavior

### 6.1 Invariants

- **INV-1** — A `TextModelConfig` with provider `meta` (as `ModelProvider.META` or the string `"meta"`) and mode `AUTO` or `VIDBYTE_MANAGED`, with no custom endpoint, is built without raising `UnsupportedProviderError`. The same holds for an agent, fallback, fork, or child whose model is a Muse model.
- **INV-2** — In `AUTO`, a `meta` call whose credentials hold a Meta key sends each attempt as exactly one POST to `VIDBYTE_GENERATIVE_GATEWAY_ENDPOINT` with exactly four headers: `authorization: Bearer <Vidbyte key>`, `content-type`, `Idempotency-Key`, and `X-Vidbyte-Provider-Key`. The last header's value is exactly the stripped Meta key, taken from `api_keys` first and from `META_API_KEY` second. The Meta key appears nowhere else in the request.
- **INV-3** — A `meta` call relays no key in two cases: in `AUTO` with no Meta key, and always in `VIDBYTE_MANAGED`. Both send exactly three headers (`authorization`, `content-type`, `Idempotency-Key`). In `VIDBYTE_MANAGED`, resolving the call's credentials never reads `META_API_KEY`, and the call never sends a key from `api_keys`. (A composition may still read `META_API_KEY` to choose its members before any call is built; see EC-16.)
- **INV-4** — A Meta key that matching bound to `meta` from `api_keys`, in either shape (INV-16), is sent only on a request whose envelope `provider` is `"meta"`. A `meta` request relays only that key or, when `api_keys` holds none, the value of `META_API_KEY`. No key that matching bound to another provider is ever sent on a `meta` request, whether in the relay header, the envelope, or the body. *Accepted exception (byok EC-14, unchanged):* `META_API_KEY` is trusted by its name, so whatever it holds is relayed on `meta` calls, even another vendor's key. Some values are refused before any request: a Vidbyte key (M-14, EC-9; `models.py:172-194`), and a value that cannot be sent in a header or is longer than 512 characters (M-21, EC-10; `models.py:172-194` and `TextModelConfig.credentials`).
- **INV-5** — Every `meta` gateway body carries the output cap as a JSON integer in `max_tokens`. The value is the caller's `max_output_tokens` exactly when one is set. Otherwise it is 32,768: the constant `VIDBYTE_MANAGED_DEFAULT_MAX_OUTPUT_TOKENS` in `vidbyte/lib/constants/jev.py`, which `TextModelRunner.__init__` applies to every gateway call (`text.py:57-62`). Every `Agent` call is the otherwise case, because an agent has no output-cap setting (§13). The SDK never adds `max_completion_tokens`, which appears only when the caller puts it in `extra_body`. *One exception:* when the caller sets `max_tokens` in `extra_body`, the SDK forwards that value unchanged, even `None`, because `extra_body` is merged last (`compatible.py:131-134`).
- **INV-6** — The envelope is exactly `{"provider": "meta", "model": <config model>, "body": <body>}`. `<body>` equals the body `MetaProvider` sends in `DIRECT` for the same config, plus the INV-5 cap. The relay header changes headers only, never the envelope.
- **INV-7** — Each `meta` gateway attempt waits at least 630 s (`VIDBYTE_GATEWAY_TIMEOUT_FLOOR_SECONDS`), and a NaN timeout becomes the floor. Every attempt of one call carries the same `Idempotency-Key` and identical headers. Two calls, concurrent or not, never share an `Idempotency-Key`.
- **INV-8** — A failed `meta` gateway call raises `ProviderRequestError(provider="vidbyte")` with the status and a reason chosen from its status alone (byok table G). The error holds no response excerpt, no chained exception, and no byte of the gateway's or Meta's body. A 409, a 502, or a non-JSON answer is re-sent at most twice, and no other answer is re-sent, a 422 included.
- **INV-9** — Neither the Meta key nor the Vidbyte key ever appears in an exception message, its `details`, its `repr`, its chained `__cause__` or `__context__`, or any log record the SDK emits during the call (captured at DEBUG on the root logger; seam in §13). Trace payloads are outside this spec's checks: the change adds no trace or log call, the Meta key travels only in a header (INV-2), and redaction of that header stays covered by byok INV-22 and its pack (`test_provider_keys_security.py:236`).
- **INV-10** — The M-12 message, which still refuses an unserved provider in a gateway mode, lists `meta` among the served providers. The M-18 message for a `meta` primary offers "Vidbyte's own meta account" as the fallback.
- **INV-16** *(r4)* — Matching proves a stripped key as `meta` exactly when it fully matches one of the two Meta shapes: `LLM_<digits>_<secret>`, the shape Meta documents, or `LLM|<digits>|<secret>`, the form #1027 cited (Q-7). In both, `<secret>` is one or more characters of `[A-Za-z0-9_-]` (D-9). Both literal prefixes, `LLM_` and `LLM|`, are reserved to `meta`: no other provider ever takes a key that starts with either, whether or not it fully matches. `meta` still takes no key that no prefix proves. So a key that starts with either prefix but does not fully match is refused at construction with M-6, before any request, with no key text in the message. This holds in every mode, `DIRECT` included, because matching runs before the mode is used.

**Must not regress:**
- **INV-11** — In `DIRECT`, a `meta` request stays byte-identical to `base_commit`: `POST https://api.meta.ai/v1/chat/completions`, `authorization: Bearer <Meta key>`, the same body (no `max_tokens` unless configured), and the caller's timeout. *(r4)* This holds for every key `base_commit` accepted. A key in Meta's documented `LLM_` shape in `api_keys`, which `base_commit` refused with M-6, now reaches Meta in `DIRECT` in the same request shape (INV-16). The behavior lives in `vidbyte/providers/compatible.py:OpenAICompatibleProvider` and `vidbyte/lib/dataclasses/model_configs.py:TextModelConfig.credentials`.
- **INV-12** — `openrouter`, `glm`, `minimax`, and `mistral` are still refused at construction in both gateway modes with `UnsupportedProviderError`, whose message names `TextModelMode.DIRECT` (`model_configs.py:TextModelConfig._require_gateway_shape`). A custom endpoint is still refused for every provider, `meta` included.
- **INV-13** — Requests for the six providers already served are unchanged byte for byte (`vidbyte/lib/http/vidbyte_gateway.py:VidbyteGatewayTransport.request`).
- **INV-14** — `StreamingTextModelRunner` still refuses `meta` in both gateway modes with `UnsupportedProviderError` at construction (`vidbyte/lib/runners/streaming_text.py:_refuse_gateway_streaming`; `meta` is not in its `STREAMING_SUPPORTED_PROVIDERS`).
- **INV-15** — The Muse price rows are unchanged. `ModelPricingRegistry.default().resolve(ModelProvider.META, "muse-spark-1.1")` returns 1.25 input, 4.25 output, and 0.15 cache read per 1M tokens (`vidbyte/lib/registries/pricing.py:284`). No row is added or edited.
- **INV-17** *(r4)* — Key matching changes only for keys that start with `LLM_`. Every other `ProviderKeyMatcher.KEY_FORMATS` row, the rows' order (anthropic, openrouter, openai, xai, gemini, meta), `FORMAT_BOUND_PROVIDERS`, `RESERVED_PREFIXES` (empty), `OPENAI_KEY_PREFIX`, `OPENAI_JWT_PREFIX`, and every message are unchanged. So `provider_of` and `accepts_unproven` give `base_commit`'s answer for every key that does not start with `LLM_` (`vidbyte/lib/registries/provider_keys.py:ProviderKeyMatcher`). No other row's prefix starts with `LLM`, and no other row fully matches a key of either Meta shape (S4 verifier's `s4v_collision.py` and this revision's `s1r4_shape_check.py`, both run in memory).

### 8.2 Patterns inherited
- **Allowlist widened when the upstream contract widens** — the gateway's served set is a closed allowlist, and refusing at construction keeps the Vidbyte key from following an unserved provider. Repo use: `vidbyte/lib/dataclasses/model_configs.py:TextModelConfig._require_gateway_shape` (byok INV-8, D-11, D-23).
- **Decorator transport, one per call** — the provider adapter builds its native body, and a per-call decorator replaces the URL and headers. Repo use: `vidbyte/lib/http/vidbyte_gateway.py:VidbyteGatewayTransport`, built in `vidbyte/lib/runners/text.py:TextModelRunner.arun`.
- **Idempotency key per call, reused across retries** — re-sends are answered from the gateway's replay. Repo use: `VidbyteGatewayTransport.request` (`Idempotency-Key`, `JEV_DEFAULT_RETRY_COUNT`).
- **Format-bound key routing** — a key whose documented prefix proves its vendor is bound only to that vendor. Repo use: `vidbyte/lib/registries/provider_keys.py:ProviderKeyMatcher.KEY_FORMATS` (Meta rule) and `FORMAT_BOUND_PROVIDERS`.
- **Fail closed on a reserved prefix** *(r4)* — a prefix the vendor documents is reserved to that vendor even when the rest of the key does not match, so an unexpected variant is refused, never routed to another vendor. Repo use: `ProviderKeyMatcher.accepts_unproven` (`@intent reserved-prefixes-only-refuse`); registries README table A: "If that is ever wrong, a real key is refused, never sent to another vendor."
- **Source-cited allowlist row** *(r4)* — each `KEY_FORMATS` row carries its first-party source in a comment and in the registries README's "Provider Key Format Sources". Repo use: every row of table F; `provider_keys.py:6`.
- **Nearest sibling: Kimi** — a bare `OpenAICompatibleProvider` subclass served through the generic gateway path. Repo use: `vidbyte/providers/compatible.py:KimiProvider`, `MetaProvider`.

### 8.3 Smaller design rejected

The smallest imaginable change is to edit nothing in the repo: Run A deploys, and developers reach Muse through `DIRECT`. It fails FR-1 and G-3, because `TextModelConfig(provider="meta", mode=AUTO)` still raises (`model_configs.py:204-209`), and Muse traffic keeps bypassing the fee. The next smallest is the constant change alone, with no README or comment edit. It fails FR-7, which `jev.py:6` requires: the README would keep telling users the gateway serves six providers and refuses Meta. The design here is that constant change, plus the docs the repo rule names, plus the test-table extensions the packs' own COMMON MODIFICATION PATTERNS require (§13).

*(r4)* For the Meta key shape, three designs smaller than D-8 were considered:
- *Change no code, and tell users to put their Meta key in `META_API_KEY`.* The README would drop its Prefixes claim. This fails FR-9 and AC-16 (i), because the §4 `api_keys` path stays broken. It also fails INV-4 and INV-16: a documented-shape key in a list beside a Kimi model still goes to Kimi (EC-17).
- *Reserve `LLM_` only, without proving it.* The misroute closes, because every `LLM_` key gets M-6. But the user's real key in `api_keys` is then always refused, so FR-9 and AC-16 still fail.
- *Prove only `LLM_` and drop `LLM|`.* This is the same size as D-8. It is the D-8 runner-up, and it waits on Q-7.

A larger design, a second Meta row for `LLM_`, was rejected: table F would hold two rows for one provider, and the table-order contract would grow, with no behavior gained over one row with two branches.

### 9.1 Data model

### 9.2 API and interface surface
- **Public library surface:** `TextModelConfig`, `TextModelRunner`, and `Agent` with every agent kind built on it now accept provider `meta` in `TextModelMode.AUTO` (the default) and `TextModelMode.VIDBYTE_MANAGED`. At `base_commit` these raised `UnsupportedProviderError` (M-12). No signature, field, default, or export changes.
- **Validation at the boundary:** unchanged, except for the Meta key rule *(r4)*. Construction refuses a custom endpoint in a gateway mode (M-13). Matching proves a key of either Meta shape, `LLM_<numeric id>_<secret>` or `LLM|<id>|<secret>`, as `meta` only. Both prefixes are reserved to `meta`, and `meta` takes no unproven key, so a malformed key with either prefix is refused with M-6 (INV-16, D-8). `credentials()` refuses a Meta key that cannot be sent or is longer than 512 characters (M-21), and a Vidbyte key in `META_API_KEY` (M-14).
- **Wire contract** (consumed, not changed): cerredz/Vidbyte#710 spec §9.2, copied in `context/wire-contract.md`. Meta's own schema lists `metadata` as an optional object (https://dev.meta.ai/docs/api-reference/chat-completions/schemas).
  - *Known discrepancy in Run A's text (r4, S4 R-11).* The wire contract's relay-header bullet calls `LLM|<app id>|<secret>` "Meta's documented key shape" (`context/wire-contract.md:16`), and Run A's backend test fakes use that form. So both shapes pass, and no SDK behavior depends on that sentence. It is a note for Run A. `context/wire-contract.md` is a verbatim copy and is not edited.
- **Error responses:** unchanged table G wording, keyed by status. The Meta-specific outcomes are the 422 for an unserved id (EC-1), the 502 for a missing backend key (EC-2), Meta's own 400 (EC-3, EC-4, EC-7), and the relayed 401 for a bad key. ### 9.4 Migrations and compatibility
- **No data migration.**
- **Behavior change:** configs and agents that use `meta` in a gateway mode used to raise `UnsupportedProviderError` and now send calls to the gateway, and those calls bill. This includes Muse fallbacks, forks, and handoffs (EC-11). No `DIRECT` call changes (INV-11), and no single-provider call that succeeded at `base_commit` changes. Compositions that tolerate a failed member or stage do change. A `meta` member that was silently skipped now runs: one more Muse member run, which is an agent loop of one or more billed calls. Examples, not a closed list, are the multi-provider grader with `provider_models` unset while `META_API_KEY` is set, aggregate proposers, fanout members, an independent critic or prosecutor/defender/judge stage under `RETURN_CANDIDATE`, a Jev run-brief writer, and *(r4, S4 R-9)* multi-agent team workers (EC-16).
- **Behavior change, key matching *(r4)*:** a key that starts with `LLM_` now proves `meta` when it fully matches, and is otherwise refused with M-6. Before, such a key was refused when no configured provider could take it, or it bound by elimination to a configured Kimi, DeepSeek, Mistral, GLM, or MiniMax model and was sent to that vendor (EC-17). This holds in every mode, `DIRECT` included. No key without the `LLM_` prefix matches differently (INV-17).
- **Merge prerequisites (§12.5):** This PR merges only after cerredz/Vidbyte#710 is deployed, after ops has provisioned the backend's `META_API_KEY`, and after the pre-merge live check described in this PR has passed. The three guard against EC-15, EC-2, and EC-3 respectively. The live check also tests A-6 (EC-18).
- **Reversal:** a revert of the set line restores the old gateway behavior. The Meta key rule should stay (see Rollback in §6.3).
- **Public contract:** no public type changes. The observable contract changes are one more member of the served set, which M-12 lists, and *(r4)* one more key prefix that proves and is reserved to `meta` in `ProviderKeyMatcher.KEY_FORMATS`.
