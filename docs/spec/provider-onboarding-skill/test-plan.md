# Test plan: provider-onboarding-skill

Spec: `docs/spec/provider-onboarding-skill/spec.md` r3 · Framework: pytest 8.3.5 (plain test functions, PyYAML 6.0.2 for the frontmatter) · Prior art copied: `tests/features/agent_output_connectors/test_output_connectors_contract.py` (static file reads, `REPO_ROOT = Path(__file__).resolve().parents[3]`), `tests/features/sdk_provider_keys/` (pack layout: README, FEATURE, `*_fixtures.py`, tests named by the failure they catch)

Pack: `tests/features/onboard_model_provider_skill/`, which holds `README.md`, `FEATURE.md`, `onboard_skill_fixtures.py` and six test modules with 65 tests: the 46 written red at S2; W7, X12, X13 and S7, added for review R-3 and R-8 with the content pins in S5, X8, X9 and A5; and S8, S9, C13 and G1 (ten cases), added for re-review round 1 (R-9 to R-12) with the content pins in X2, X4, X5, X7, X10, A3, A4, S4, C10 and W7; and S10 and W8, added for S5 repair 3 (spec r9 row s5r3-1). Codes in brackets (A1, C4, W6, X3, S2) are the pack's own test codes, written in each test's first comment and in `FEATURE.md`.

The deliverable is Markdown an agent executes, so most tests are static contract tests over the two skill files and `REPO_MAP.md`. The integration tests run the skill's own `sed -n 's/…/…/p'` extraction commands, through a POSIX BRE emulator in the fixtures, over the real repository files and the real wiring table. They also check every path and symbol the checklist names against the tree. The D-29 test calls the real `Runner._normalize_provider_and_model`. No test reads git state, the network, `gh` or Claude, and no test pins the provider list, the member count, `PRICING_AS_OF` or a line number, so every test stays valid inside every provider PR the skill opens (spec §13, R-1).
