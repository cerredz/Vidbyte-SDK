WHAT THE IMPLEMENTATION GETS RIGHT (max 4 bullets, concrete, so nobody "fixes" what works)
- The runtime is the inherited linear loop plus exactly three hooks (`_after_tool_iteration`, `_continue_finish_attempt`, `_budget_stop`) and one private step. It calls `super().arun` once. The rebuild calls `ContextCompactionEngine().compact_provider_messages(..., TRIM_WITH_PROVIDER_BOUNDARIES, {"max_messages": 1})`, assigns `messages[:] = list(kept)`, runs from both hooks (on a refused finish it runs before the gap message), and is counted only when `removed_count > 0` (runtime.py:136-177). This is D-11/INV-30 as the user decided. Do not change it.
- The roles are enforced by the catalog, not by the prompt. Live handles are matched to a role only by their queued name `browser-<role>-<n>` (tools.py:47). The orchestrator's run catalog is `self.tools.without(action).extend((episode, goal.tool()))` (runtime.py:116). Workers get the very same bridged ACTION tool objects, so every episode shares one server process (INV-5, INV-7, AC-5, AC-6).
- Goal card and recheck: the card is a frozen record. `patch_goal` takes the section as an enum and accepts only plan/progress/blockers, and progress only grows. Each recheck is a newly built `BaseAgent` with `system_prompt_presets=()` that is given only the goal, done_when, and progress (goal.py:228-260). The stall rule follows D-14 exactly (goal.py:126-145). These are the user's "patch tool can only touch the mutable three" and "Fresh context is the part that matters".
- Keys come only from `BrowserServerSettings.env`, checked by the canonical `McpPresetRegistry.build_config`. `env` and `api_keys` are `repr=False`, and `os.environ` is never read. Every cap is a constant plus a check in code, and the 19 prompt leaves contain no digit. The class-size requirement holds: the largest module is 251 body lines and the largest class is 166 lines.
