## What it does

Starts subagent pairs that each carry out one task, so the work happens outside your own context. In every pair, a fresh generator does the task from its generator_prompt, then a fresh verifier checks the result against the done criteria from its verifier_prompt, fixes what it can, and ends with a verdict. Every task therefore needs both prompts. Only the result card comes back: what the pair produced stays in the workspace and in memory, where you and later pairs can find it, so work that would have cost your context many tool results costs it one card.

## When to use it

Use it for any piece of work that would fill your context: reading sources, producing substantial content, or anything that takes many tool calls. Do work yourself only when it is quicker than writing a task card for it. A long source you need only a few facts from is worth a pair too: ask for those facts, and the source never enters your context. Delegate by deliverable rather than by step, so each pair produces something whole that its verifier can check on its own terms. Put independent deliverables in one call so they run at once, and hold back work that depends on another task's result until you have read that task's card. Every card of a call lands in your context at the same moment, so size each call to what you can read and act on.

## How it behaves

All the tasks of one call run at the same time, and the call returns once every pair has finished, with one short result card per task in the order you wrote them. A card carries the generator's status, the verifier's verdict, a capped summary and review, the memory entries saved and dropped, and the files written, never the agents' conversations. The summary, the review, and the lists of dropped entries and files are each cut to a fixed length, so have each pair keep its detail in a note the card can point to.

Both agents start fresh: each sees its own part of the task card, the workspace map, and the shared workspace, but not this conversation, and only the generator receives the context the card names. Neither can ask you anything, so whatever the card leaves out, the pair does not know: write every card to stand on its own, with the terms, decisions, and constraints its task depends on stated in it or named in its context. Spell out any shorthand or name you coined in this conversation, since the pair has never seen it. Before you write a card, check the map and search memory for what earlier pairs found, and name what applies in the context, so the pair starts from it instead of finding it again. The fields work together, and each is described on its own parameter: the goal is the outcome, the done criteria are how that outcome will be judged, the generator_prompt is how to reach it and what to report, and the verifier_prompt is what to check it against. Make them agree, because the verifier never sees the generator_prompt: a requirement stated only there is never checked, and a generator_prompt that contradicts a criterion sets the pair up to fail. Say in the generator_prompt which findings deserve an entry, if any, because the pair cannot know what later tasks will need. Name in the card only the entries, paths, and tools the pair needs, since each one fills its context before it starts.

A pair's memory entries are saved only once its verifier gives a verdict, while the notes it writes take effect at once, so the files a failed pair wrote stay in the workspace for a corrected task to fix or replace. The verifier reviews every entry the generator staged and drops the ones that are wrong or not worth keeping, so the entries on a card have passed that review, and a card without a verdict saved none. Saved entries are live as soon as the card comes back, so your next cards can name them in their context. One pair's failure, even an error, becomes its own card and never stops its siblings; a generator that fails gets no verifier, so its card comes back unchecked. To check such work without redoing it, launch a new task whose context names the files it wrote. Pairs a generator launches report to it, not to you, so their work reaches you only through its card and the files they wrote. A task whose name already finished in this run, among the tasks you launched, is not run again: its recorded card comes back under a replayed label. Give new or repeated work a new name. Launching a finished name again is also how you reread its card after your history has trimmed it.

## Rules and refusals

The whole batch is checked before anything starts, and any problem refuses the whole call with a message that says what to fix. A refused call starts and records nothing, so correct the cards and call again. Names must be unique within the call, context may name only live entries, and tools may name only extra tools you hold. The system also limits how many tasks one call may carry, how deep pairs may nest, and how many agents one run may start; a call over a limit is refused with a reason that names the limit. Then split the batch over several calls, launch fewer tasks, or do the work yourself.

Never ask for a transcript: a pair that reports every step it took spends its card on history and crowds out the findings you need. Never paste a large excerpt into a card field either, since everything you write into a card also stays in your own context; name the file or entry in the context instead, so the generator reads only the part it needs.
